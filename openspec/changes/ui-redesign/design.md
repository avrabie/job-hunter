## Context

Observed in `ui/`: React 19, react-router 8, no UI library, `src/index.css` is the only stylesheet; pages render `<main>` with a 32 rem max width; `pages/Home.tsx` switches loading/error/signedOut (`Landing`)/signedIn (`Shell`, a button grid plus a backend ping); the CSP in `ui/nginx/security-headers.conf` is `default-src 'self'; script-src 'self'; style-src 'self'; img-src 'self' data:; connect-src 'self'`. 597 tests (vitest + testing-library) pin behaviour, labels and roles; the profile page alone has a 1 578-line test. The backend `cv/export/SkillGroups.kt` already groups skills by whole-token keyword match (LANGUAGES, FRAMEWORKS, MESSAGING, SECURITY, CLOUD, TESTING, DATABASES, TOOLS, OTHER).

## Decisions

1. **Design tokens first.** `ui/src/styles/tokens.css` defines `:root` custom properties (colour roles: bg, surface, text, muted, primary, primary-contrast, border, success, warning, danger; type scale; spacing 4-pt scale; radius; shadow; focus ring) with a dark override under `@media (prefers-color-scheme: dark)`. Components use only tokens. Contrast: WCAG AA for text and focus rings in both themes. The existing accent `#1f5fbf` stays the primary hue.
2. **CSP-safe by construction.** One external stylesheet bundle built by Vite; no `style` attributes, no `<style>` in JSX, no inline event handlers; icons are inline SVG elements (allowed); fonts, if any, are self-hosted woff2 files under `ui/public/` or imported assets (system font stack by default; a self-hosted Inter/Source Sans 3 variable font is allowed if the size stays under 150 KB). `ui/test-image.sh` must still pass.
3. **Layout and navigation.** A `Layout` component wraps signed-in routes: skip link, `NavBar` (`<header><nav aria-label="Main">`), `<main id="content">`, small footer. Content width: 72 rem max for lists and tables, 48 rem for forms/reading pages (a `page--narrow` modifier). NavBar items: Postings, Matches, Job tracking, CV (a menu with Export and Public page), Profile, Admin (ADMIN role only), then the identity and Sign out at the right. Under 48 rem the items collapse behind a hamburger button (`aria-expanded`, `aria-controls`, Escape closes, focus handled). The active item has `aria-current="page"`. Signed-out pages (landing, register, callback, error) use a minimal header (brand, Sign in, Register).
4. **Home (signed in)** is a short overview: greeting, three cards (Matches, Job tracking with counts per stage from the existing list endpoint, Profile completeness hint if cheap) and a small "Service status" line in the footer replacing the old "Check again" panel. No new endpoints.
5. **Landing page** is static content (no API call) built from data constants for the six capability cards and three steps, so copy changes are one-file edits. Sections: hero (headline, one sentence, Sign in primary, Register secondary), capabilities grid, how it works, privacy and control, final call to action. Capability copy is taken from what is actually shipped (see `docs/architecture.md` and the specs) and avoids promising anything not built.
6. **Collapsible sections** use native `<details>`/`<summary>` (accessible, no JS state needed), wrapped in a `Collapsible` component with a summary line (count or status) and a controlled `open` for "Expand all / Collapse all". A section with a validation error opens itself and receives focus (the existing "focus after a failed save" behaviour must keep working). Unsaved-edit protection is unaffected.
7. **Skills grouping in the profile.** `ui/src/profile/skillGroups.ts` ports the keyword table and whole-token rule from `SkillGroups.kt`; both read the shared fixture `skillGroups.cases.json` in their tests (precedent: `paragraphs.cases.json`). The Skills section shows groups in a fixed order, each a `Collapsible` with its count, skills sorted by level then name; a filter box narrows by name across groups (groups with no match hide); groups start collapsed when the list is longer than 20 skills, open otherwise. Editing a skill, adding, removing and the analysis-origin hints keep working inside the groups; a new skill without a recognised keyword lands in OTHER. Grouping is display only: the saved order and data do not change.
8. **Migration of pages.** After group 1 exists, pages are converted one by one: replace local markup/classes with the shared components, keep every accessible name, role and label that tests rely on; tests change only where layout wrappers moved. The old global rules are deleted once no page uses them.
9. **Verification without a local browser.** The owner reviews on prod (standing preference). Agents verify with tests, `tsc`, oxlint, prettier, `vite build`, and the image script; the lead adds a lightweight check that the built CSS contains no `style=`/inline patterns and that the HTML has the skip link, nav landmark, and one `h1` per page. Deploy in two steps: (A) design system, shell/nav, landing, profile; (B) all remaining pages. The owner's feedback after A adjusts tokens before B.

## Contract

- No API or event changes. New files: `ui/src/styles/{tokens,base,components}.css`, `ui/src/layout/{Layout,NavBar,Footer}.tsx`, `ui/src/ui/{Collapsible,Card,PageHeader,Badge,EmptyState,Alert}.tsx` (names may follow existing conventions), `ui/src/pages/{Landing,Home}.tsx` rewritten, `ui/src/profile/{skillGroups.ts,skillGroups.cases.json}`, backend test change in `SkillGroupsTests` reading the same fixture (copied into test resources by the Gradle build or referenced by path; the agent picks the existing paragraphs mechanism).

## Risks / Trade-offs

- A broad change can break accessible names that tests and users depend on; mitigated by converting page by page with the test suite green at each step.
- Without browser screenshots the first look may need a round of owner feedback; deploy A early for that.
- Two skill-group tables (Kotlin, TypeScript) can drift; the shared fixture test catches it, a later change could expose groups from the API.
- Dark-mode contrast is easy to get wrong; tokens are defined once and checked by a small contrast test in code.
