# Design

## Context

- `postings` (shared, no owner): `PostingQuery.find(id)` returns `Posting` with `description` (plain text, HTML already stripped by the Greenhouse mapping), `url`, `links`, `language`, `firstSeen`, `lastSeen`, `contentHash` internally. Descriptions are overwritten on re-crawl and rows are never deleted. The UI already shows `/postings/:id`.
- `applications` and `notifications` exist only as empty Java `package-info` modules named in `ModularityTests` (eleven modules). Controllers live in the module they belong to (`cv`, `files`, `matching`).
- `llm` is the only module that imports Koog; `KoogCvReader` and `KoogProjectAnalyst` show the pattern (one request, manual JSON mode, timeout, `LlmFailure` with fixed messages, `ExecutorSource` seam, `FakePromptExecutor` in tests). `ProjectAnalysisController` uses `AnalysisLimiter` (a `UserHourlyLimiter`) and maps `LlmFailureKind` to 503/502.
- The profile is read through `ProfileService.get(sub)`. `profile` must not import `cv` or `llm`; `llm` imports `profile`. The `export` code maps experience entries to text, and the UI knows entries by array index.
- Owner decisions: stages exactly INTERESTED, APPLYING, APPLIED, REJECTED; a separate Job Tracking page; the letter is Markdown text, reviewed, commented and regenerated with the comments; it is built from the job description and the relevant experience or projects. Assumption recorded: re-fetching the live job description when the user marks interest is **not** part of v1 (the stored text is at most one crawl old and the page shows when it was captured and last seen); it can be added as a `sources` call later without changing this design.

## Goals / Non-Goals

**Goals:** per-user tracking with a frozen job description; letters generated from chosen facts, reviewable, commentable, regenerable, downloadable; safe handling of untrusted job text; same limits and logging discipline as the other model features.
**Non-Goals:** sending email or applying on the user's behalf; PDF letters; reminders or notifications (the `notifications` module stays empty); calendar of interviews; automatic matching score; multiple users per application; letter templates by the user; re-fetching the live posting.

## Decisions

1. **Module `applications`.** Public API `ApplicationService` (track, get, list, update, remove, `frozenJob(sub, id)`), implementation and controllers in `applications/internal`; it reads `postings` (`PostingQuery`), `profile` (`ProfileService`) and `llm` (`LetterWriter`) only through their public APIs. Letter code lives in the same module (`applications.letters`, public types in `net.s4v3.backend.applications`, the rest internal). `ModularityTests` keeps eleven names; the Java placeholder is replaced by Kotlin sources (delete its `package-info.java` only if Kotlin module detection needs it; the agent checks the rule). `llm` must not import `applications`: `LetterWriter` takes plain request types defined in `llm`.
2. **Tables (two changesets after `moldo:015`).** `application(id uuid pk, owner_sub text, posting_id uuid null, stage text, title text, company text, url text, description text, job_language text, captured_at timestamptz, posting_last_seen timestamptz null, content_hash text, notes text, applied_on date null, stage_changed_at timestamptz, created_at, updated_at, unique (owner_sub, posting_id))` and `motivation_letter(id uuid pk, application_id uuid fk on delete cascade, owner_sub text, version int, language text, text text, how text (GENERATED|REGENERATED|EDITED), selection jsonb, instructions text, comments jsonb, based_on_version int null, created_at, unique (application_id, version))`. `posting_id` has no foreign key: the posting can disappear and the copy is self-contained. `content_hash` of the live posting at capture time lets the list say `liveChanged` by comparing with the live posting's current hash (exposed by `PostingQuery` as part of `Posting`, added minimally if missing). Indexes on `(owner_sub, stage_changed_at desc)`.
3. **Endpoints (all authenticated, owner from the token).** `POST /api/applications {postingId}` (200 existing or 201 new), `GET /api/applications?stage=`, `GET /api/applications/{id}`, `PATCH /api/applications/{id} {stage?, notes?, appliedOn?}`, `DELETE /api/applications/{id}`, `GET /api/applications/by-posting?ids=...` (stages for a page of postings, max 100 ids, used by the postings list), `POST /api/applications/{id}/letters` (generate or regenerate), `POST /api/applications/{id}/letters/edited` (manual), `GET /api/applications/{id}/letters`, `GET /api/applications/{id}/letters/{version}`, `GET /api/applications/{id}/letters/{version}/download`, `DELETE /api/applications/{id}/letters/{version}`. Errors as `{"error": code}` through `ErrorResponses`; others' resources 404.
4. **Generate request.** `{language: EN|DE|null, experience: [int], projects: [int], skills: [int], instructions: string?, basedOnVersion: int?, comments: {general: string?, paragraphs: [{n: int, text: string}]}}`. Indexes refer to the **saved** profile's lists at request time (the server resolves them; out-of-range is 400 `selection_invalid`). With `basedOnVersion` the call is a regeneration from that version's text; without it, a first draft. The server never accepts profile text from the client.
5. **LetterWriter (llm).** `fun write(request: LetterRequest): String` where `LetterRequest(job: JobText(title, company, description), candidate: Candidate(fullName, experience: List<Profile.Experience>, projects: List<OpenSourceProject>, skills: List<Skill>), language, instructions: String?, previous: PreviousLetter?(text, comments))`. One plain-text Koog request (not structured JSON): system prompt file `LetterPrompts` (constants) with the rules of the spec; user prompt template with sections `<job_description>` (delimiters, data only), `<candidate_facts>`, `<instructions>`, and for regeneration `<previous_letter>` and `<review_comments>` (comments numbered by paragraph). Description truncated to 20 000 chars before sending (at a paragraph edge). Output cleaning: strip a surrounding code fence, trim, reject empty, reject if it contains `<` followed by a tag-like name (HTML), cap 6 000 characters (refuse, not truncate). Model: the configured one (`Haiku_4_5` default is cheap but weaker at writing; add `jobhunter.letters.model` default to the same as `jobhunter.llm.model` so the owner can switch to Sonnet in config without code). Timeout 60 s. `LlmFailure` only.
6. **Injection and invention.** Delimited data plus explicit rule; the model is never given tools; its output is only text shown as text. Invention cannot be fully prevented: the system prompt lists only the chosen facts as allowed, the UI shows the checking notice, and the review loop is the control. A fake-model test records the request and asserts the delimiters, that the instructions sit outside the data block, and that no unchosen profile field (preferences, contact data, work authorisation) is present.
7. **Limits.** `LetterLimiter` (a `UserHourlyLimiter`, `jobhunter.letters.per-hour` default 20) shared by generate and regenerate; manual edits do not count. Selection caps in spec. Versions per application 20. Applications per user 500. Text 6 000 chars, notes 5 000, comments 500 each (20), instructions 1 000.
8. **Download.** Same file-name normalisation as `DefaultExportService.fileName` (extract to a shared helper only if it stays trivial; otherwise copy with a test). Headers: `Content-Type: text/markdown; charset=utf-8`, `Content-Disposition: attachment; filename=...`, `X-Content-Type-Options: nosniff`, `Cache-Control: no-store`.
9. **UI.** `ui/src/applications/`: `applicationsApi.ts`, `ApplicationsPage.tsx` (grouped by stage), `ApplicationPage.tsx` (notes, frozen JD, notice) and `LetterWorkspace.tsx` (selection form built from the profile via the existing profile API, versions, paragraph comments, edit, copy, download), `InterestedButton.tsx` used by `PostingsPage.tsx` and `PostingPage.tsx` (stages for the visible postings loaded with `by-posting`). Letter text is rendered with React text nodes inside `<p>` per paragraph (paragraphs split on blank lines, the same split the server uses for comment numbers); Markdown is not rendered as HTML in v1 (it is shown as the plain Markdown source, which is what the user copies). Routes added in `App.tsx`; nav entry in `Shell.tsx`. Texts English.
10. **Paragraph numbering.** One function, `paragraphs(text): List<String>` (split on one or more blank lines, trimmed, empty dropped), implemented in Kotlin and in TypeScript with a shared test table of cases so the numbers agree.
11. **Privacy.** Logs carry only outcome, version number, duration and counts. Tests use `captureAppLogs` with sentinel words in the description, profile and comments. Synthetic data only ("Ada Example", "Employer1 AG", invented job texts).

## Risks / Trade-offs

- Letter quality depends on the prompt and model. Mitigation: prompts are code with pinned rule tests; the lead tries them with synthetic data on the real model after deploy and adjusts (task 0.1); model switchable by config.
- A model can invent facts. Mitigation: only chosen facts, explicit prohibition, visible notice, review loop.
- The frozen copy is plain text (no formatting), as stored today. A richer description is a separate change.
- Stage `REJECTED` etc. are user-set; nothing reads the employer's side.
- `applications` becomes a real module: dependency direction must stay `applications -> postings, profile, llm`; checked by `ModularityTests`/ArchUnit.

## Migration Plan

Two additive changesets; no data migration. Deploy backend first, then the UI. Rollback: redeploy the old images (tables stay, unused).

## Contract

- Types: `ApplicationStage {INTERESTED, APPLYING, APPLIED, REJECTED}`; `ApplicationSummary(id, postingId?, title, company, stage, appliedOn?, stageChangedAt, liveStatus {OPEN, CHANGED, GONE?})`; `ApplicationDetail` adds `url, description, capturedAt, postingLastSeen?, notes, letterCount`. `GONE` means the posting was not seen for 14 days or no longer exists.
- `LetterSummary(version, how, language, createdAt, basedOnVersion?)`; `LetterDetail` adds `text, selection, instructions, comments`.
- Endpoints and request shapes of decisions 3 and 4; errors: `selection_invalid` 400, `letter_text_invalid` 400, `application_limit` 409, `letter_limit` 409, `letter_not_configured` 503, `letter_failed` 502, `rate_limited` 429 (existing helper), 404 for others' or unknown ids.
- `LetterWriter.write(LetterRequest): String`; `paragraphs(text)` rule of decision 10.
