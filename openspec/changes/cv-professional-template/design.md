# Design

## Context

- `cv.export`: `CvBuilder` (profile + `ExportOptions` to `CvDocument`), `HtmlRenderer`, `PdfRenderer` (openhtmltopdf, bundled Source Sans 3), `Templates` (one inline CSS per template, CSS 2.1 only: floats and tables), `Labels`. `CvDocument` has `name, headline, contactLines, facts, sections` with `ProseSection | EntrySection | TagSection | LineSection`.
- `cv.publiccv`: `PublicCvSettings` is stored as a JSON column, so a new nullable field needs no migration; the render cache key is `(owner sub, profile version, settings version, ...)`; `/api/public/cv/**` is already open in `SecurityConfig` and the controller has a catch-all uniform 404.
- `files`: `FileCabinet` exposes only `masterCv(sub)`; storage and records are `internal`. Skills in the profile have no category.
- The sample look is described in the proposal. The sample file itself is personal data in git-ignored `private/sample/`; no agent may copy text from it into code, tests or docs. Colours are approximate: navy `#1f3a68`, orange `#c0792a`, body text `#222222`, rule navy 1.5 pt.
- Owner decisions: skills are auto-grouped by technology type; the photo may also be on the public page.

## Goals / Non-Goals

**Goals:** a Professional template that looks like the sample; a safe photo pipeline shared by export and public page; no new dependency.
**Non-Goals:** user-defined skill groups; photo upload UI (the file cabinet already uploads files); other image types than JPEG; cropping controls (always centre crop); a photo in Markdown, Classic, Modern or Compact.

## Decisions

1. **Template, not a mode.** `CvTemplate.PROFESSIONAL`. `Templates.css` gets one more block. Renderers that ignore templates (Markdown) are unchanged. CLASSIC, MODERN and COMPACT output must stay byte-identical (a test compares against stored expectations built from the current code before the change).
2. **Document model.** `CvDocument` gets `photo: CvPhoto?` (`bytes: ByteArray`, always the processed JPEG) with default null, and a new section type `GroupedTagSection(title, groups: List<TagGroup(name, tags)>)`. `CvBuilder` produces `GroupedTagSection` for skills only when the template is PROFESSIONAL; every other renderer path receives the flat `TagSection` as before. The Markdown renderer never sees it.
3. **Skill groups.** `SkillGroups` (internal object, one Kotlin map): group id to a list of lowercase keywords, matched against the skill name lowercased, on whole tokens (split on spaces, `/`, `,`, `(`, `)`; the symbols `c++`, `c#`, `.net`, `node.js` match as whole names). Groups in print order: LANGUAGES (java, kotlin, python, c, c++, c#, rust, go, scala, typescript, javascript, sql, pl/sql, julia, r, php, ruby, swift, bash), FRAMEWORKS (spring, spring boot, webflux, hibernate, jpa, react, angular, vue, django, flask, quarkus, micronaut, jax-rs, jsf, jsp), MESSAGING (kafka, activemq, rabbitmq, jms, mqtt, nats, pulsar), SECURITY (oauth2, oidc, jwt, saml, mtls, scim, keycloak, tls, sso), CLOUD (azure, aws, gcp, docker, podman, kubernetes, rancher, terraform, helm, hetzner, openshift, pcf, ansible, linux, rhel), TESTING (junit, mockito, testcontainers, selenium, cypress, jest, playwright, gatling, jmeter, elk, opentelemetry, otel, prometheus, grafana), DATABASES (oracle, postgresql, postgres, mysql, mariadb, mongodb, cassandra, redis, h2, sqlite, elasticsearch, neo4j), TOOLS (git, gitlab, github, maven, gradle, jenkins, jira, intellij, ci/cd), OTHER. A skill name with several matching words goes to the first group in print order that matches. Labels are in `Labels` (EN and DE, all nine). Skill levels print as in the flat list. The list is data, small and explicit; the tests pin the examples of the spec.
4. **Photo pipeline (one class, `PhotoProcessor`, in `cv.export`, public API so `publiccv` can use it).** Input: the file's path and size from `FileCabinet.image`. Steps: reject if size > 6 MB; open an `ImageInputStream`, take the first JPEG `ImageReader`, read the width and height **before** decoding and reject if either exceeds 12 000 or width x height exceeds 16 000 000; read the EXIF orientation from APP1 (1, 3, 6, 8 applied, others as 1); decode (`ImageIO`) with source subsampling so the short side stays between 2x and 4x the target (about 8 MB of heap for a 16 MP photo), convert any colour model to RGB (`TYPE_INT_RGB`), centre-crop to a square, scale to 320 x 320 with bilinear then a high-quality step (`Image.SCALE_AREA_AVERAGING` or two-step), paint on a white background through a circular clip with antialiasing, write with `ImageWriter` at quality 0.9 with no metadata. Output bytes are deterministic for the same input. All failures (unreadable, CMYK that cannot convert, truncated) map to one `InvalidPhotoException` without a cause message that includes names. Headless: `java.awt.headless=true` is set already for the PDF renderer; the Paketo tiny JRE already runs PDFBox with `ImageIO`, and the lead checks `ImageIO` JPEG read and write in the production image before deploy (task 0.1). Rendering a photo costs about 20 ms; the result is cached with the page.
5. **HTML and PDF.** The photo is a `data:image/jpeg;base64,` `<img>` in a header table (name and contact left, photo right, 34 mm round image). CSP meta is `default-src 'none'; style-src 'unsafe-inline'` plus `img-src data:` only when `document.photo != null`. openhtmltopdf renders data URIs natively. The round shape is in the pixels (white corners), so no `border-radius` support is needed. Footer: `@page { @bottom-center { content: ... } }` with the name and headline as a string; if the renderer lacks margin-box support, a fallback is a `position: running(footer)` element; the agent tries margin boxes first and records what worked. Section headings: `letter-spacing: 3pt`, 11 pt, navy, bottom border. Entry header: a two-cell table (title left bold navy, period right bold navy), second row company (orange bold) left and place (italic grey) right. Bullets: `list-style-type: square` with the bold lead-in produced from the text before the first `: ` when it is shorter than 40 characters (the same rule as the sample); no bold if there is no colon. Justified summary: `text-align: justify`. Page numbers are not required.
6. **Export API.** `ExportOptions.photoFileId: UUID?` (default null) and the request body field `photoFileId`. `DefaultExportService` reads the photo through `FileCabinet.image(sub, id)` only when template is PROFESSIONAL and format is not Markdown; null or invalid raises `InvalidPhotoException`, which the controller maps to 400 `{"error":"photo_invalid"}` using the existing error helper. The cabinet is read by `sub` from the token, never from the request.
7. **File cabinet API.** `FileCabinet.image(sub, id): CabinetFile?` implemented in `FileCabinetService`: `JdbcFileRepository.find(sub, id)` (owner scoped), size <= 6 MB, read the first three bytes from storage and compare to `FF D8 FF`. Null for everything else. No logging of names.
8. **Public page.** `PublicCvSettings.photoFileId: UUID? = null` (JSON, backward compatible). Saving: validate with `FileCabinet.image` when set (400 `photo_invalid`); the setting stays null unless the template is PROFESSIONAL on save is **not** enforced (the id is kept but unused with other templates, so switching back works). Rendering the page: `photo` is passed to the builder only if template is PROFESSIONAL and the image still loads, else the page has no photo and no error. Photo route `GET /api/public/cv/{handle}/photo` (HEAD too) in `PublicCvPageController`: same checks as the page (published, not locked, found), same per-IP and 404 limiters, answers `image/jpeg` with `Cache-Control: no-cache` plus the ETag (SHA-256 of the bytes), `X-Content-Type-Options: nosniff`, `Content-Security-Policy: default-src 'none'; sandbox`, `Content-Disposition: inline; filename="photo.jpg"`. Every other case is the existing uniform 404. The single-segment handle route must not capture `…/photo`, and `…/photo` for an unknown handle must look like any other 404. The render cache key adds `photoFileId` and the file's `(sizeBytes, sha256)` read from the cabinet; the processed photo is cached beside the page (one entry). A file deleted or replaced changes the key. Audit flags add `photo`. The settings JSON of existing rows reads with `photoFileId = null`.
9. **UI.** `ExportPage` and `PublicCvPage` list JPEG files from the existing files API (`contentType` image/jpeg or name ending `.jpg`/`.jpeg`, case-insensitive; the server is the final judge). Options types gain `photoFileId`. The public page shows the warning text. Texts are English like the rest of the UI. No image is rendered in the picker (names only), so no image loading in the UI.
10. **Privacy.** The photo and its id never appear in logs, errors, audit rows or the `README` examples. Test photos are synthetic generated images (a gradient drawn in the test), never a real face. The sample PDF stays in `private/`.

## Risks / Trade-offs

- Auto-grouping will sometimes put a skill in the wrong group or "Other"; the list is small and extendable, and the group is only a layout aid. A later change can let the user name groups.
- A public photo is the first public endpoint serving a user's image. Mitigations: off by default, explicit warning, re-encoded small image without metadata, same 404/limits as the page, taken down with the page, no listing.
- Decoding untrusted JPEGs: size and pixel caps before decoding, a 2-parallel guard shared with PDF rendering (reuse `RenderGuard` permits) so decoding cannot exhaust the heap.
- PDF footer support in openhtmltopdf: verified in tests; fallback described in decision 5.
- The round mask makes the corners white: on the public page the background of the Professional template is white, so it is invisible.

## Migration Plan

Deploy backend and UI together (the UI sends `photoFileId` and `PROFESSIONAL`). Old UI against new backend still works; new UI against old backend would fail on the unknown template, so deploy backend first. Rollback: redeploy the previous images; stored `photoFileId` fields are ignored by the old code.

## Contract

- `CvTemplate`: `CLASSIC | MODERN | COMPACT | PROFESSIONAL`.
- `POST /api/cv/export` body adds optional `"photoFileId": "<uuid>"`; error `400 {"error":"photo_invalid"}`.
- Public settings JSON adds `"photoFileId": null | "<uuid>"`; same 400 on save.
- `GET|HEAD /api/public/cv/{handle}/photo` -> 200 `image/jpeg` or the uniform 404.
- `FileCabinet.image(sub: String, id: UUID): CabinetFile?`.
- `PhotoProcessor.process(file: CabinetFile): ByteArray` (320 x 320 JPEG), throws `InvalidPhotoException`.
- `CvDocument.photo: CvPhoto?`; `GroupedTagSection`, `TagGroup`.
- `SkillGroups.group(skillName: String): SkillGroup` and `SkillGroup` enum in print order with EN and DE labels in `Labels`.
