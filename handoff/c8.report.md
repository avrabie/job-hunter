# C8 report: shared provider cache (profile module)

Status: done. Not committed.

## What changed
- New `backend/src/main/kotlin/net/s4v3/backend/profile/internal/ProviderCache.kt`:
  `internal class ProviderCache<V : Any>(ttlMinutes, maxEntries, now = System::nanoTime)` with
  `get(provider, name): V?` and `put(provider, name, value)`. The key is (provider, name.lowercased()).
  Eviction is unchanged: on a store at or above `maxEntries`, expired entries are removed first.
- `DefaultRepositoryCatalog.kt`: its `CacheKey`, `Cached`, `store` and cache imports removed; uses
  `ProviderCache<RepositoryListing.Found>(ttlMinutes = 5, maxEntries = 1000)`. Only `Found` is stored.
- `DefaultRepositoryDigestSource.kt`: same change with `ProviderCache<DigestResult.Found>` and TTL 10.
  `isValidFullName` and `nameSegment` are untouched (the other agent's edit area).
- New test `backend/src/test/kotlin/net/s4v3/backend/profile/internal/ProviderCacheTests.kt` (plain JUnit, no Spring):
  hit before TTL, miss at TTL, key case-insensitive, at maximum expired entries are dropped and live ones kept.

## Kept as is
- The `byProvider` map and its `require` stay in each class. The two messages differ
  ("one repository provider per value" / "one repository digest provider per value"), and moving them
  into the cache would not make it simpler.
- Public signatures, constructors, class names, TTLs and the invalid-name checks are unchanged.

## Findings
- The size cap is soft, as it was before. The sweep only removes expired entries. If every entry is still
  live when a store happens at the maximum, the map grows past 1000. The behaviour is kept on purpose
  ("same eviction behaviour"), but a hard cap would be a behaviour change, so it is a decision for the owner.
- Diff is limited to the cache code, the two import blocks and the new files. No doc change.
